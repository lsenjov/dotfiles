01 · Executive decision

Use Stow as the deployment layer.

Keep authored files readable in Git, package them by concern, and make installation reversible. Retain the cleaned personal Prezto fork as a pinned dependency; flatten personal skills into this repository.

Recommended: GNU Stow monorepo

Stow mirrors the shape of $HOME, operates in explicit packages, supports visible dot-* source names, and detects conflicts before it changes the target tree. It is a small conceptual layer over ordinary files and symlinks.

Not a bare home-directory repository

A bare repository has fewer dependencies, but it makes broad home-directory operations easier and gives weak structural protection against accidentally tracking Codex runtime state.

Chezmoi remains the escalation path

Move to chezmoi only when host templates, several operating systems, encrypted files, or password-manager integrations become central requirements.

04 · Prezto migration

Preserve the fork; normalize the home layer.

The cleanup has made the personal fork suitable for pinning directly. The migration should avoid copying its working tree into the main repository, stripping its Git metadata, or changing the pinned revision during deployment.

  1. Add lsenjov/prezto as packages/zsh/dot-zprezto at revision 6c4fdc9, with recursive submodules.
  2. Keep the removed Powerlevel9k checkout out of the migration; Powerlevel10k is the configured prompt dependency.
  3. Represent five standard runcoms as relative links into the pinned fork.
  4. Make dot-zshrc a first-party wrapper that adds ~/.local/bin portably, when present, and then sources the fork’s runcoms/zshrc. This preserves revision 6c4fdc9.
  5. Store .p10k.zsh directly in the Zsh package.
  6. Document that Prezto updates happen by advancing the submodule revision, testing it, and committing the pointer.
↻

Update discipline

Do not use zprezto-update as the normal update path after installation. It can advance the submodule working tree without updating the dotfiles repository’s recorded revision.

05 · Codex and skills

Track authored behavior, never generated state.

Global instructions and global skills live in different canonical locations. The deployment packages should reflect that boundary and keep runtime data out of Git.

Global guidance

Deploy the personal instruction file to ~/.codex/AGENTS.md. Keep a separate root AGENTS.md for rules that govern this repository.

Global skills

Deploy personal skills to ~/.agents/skills, the current canonical user scope. Do not copy bundled ~/.codex/skills/.system content.

Flatten personal repositories

Import grill-me, explain-code-changes, and code-review-skill as ordinary directories. Preserve the nested explain-code-changes repository and the externally symlinked code-review-skill repository before flattening; grill-me is covered by the parent ~/.codex repository.

Attribute external material

Restore and verify the missing LICENSE.txt for frontend-design. Record source URLs and imported revisions in ORIGIN.md when a skill is not wholly first-party.

Explicit exclusion list

  • auth.json
  • session transcripts
  • history files
  • logs and shell snapshots
  • SQLite databases and WAL files
  • model and HTTP caches
  • installation identifiers
  • plugin installation caches
  • bundled .system skills
  • credentials or private keys

Before flattening, create both git bundle archives and metadata-preserving working-tree archives for explain-code-changes and code-review-skill. The latter archive must include the modified SKILL.md and untracked reference/cross-cutting/duplication.md that a bundle cannot capture. Generate file and SHA-256 manifests, import the working trees without .git, and compare the imported manifests before removing any original metadata. After the new links are verified, separately bundle the parent ~/.codex repository—which covers grill-me—and then remove its .git directory.

06 · Bootstrap contract

Preview first. Apply second. Undo cleanly.

The bootstrap must be idempotent and conservative. It should never use broad deletion, silently elevate privileges, or let Stow fold the complete Codex runtime directory into the repository.

git clone --recurse-submodules <repo-url> ~/code/lsenjov/dotfiles
cd ~/code/lsenjov/dotfiles
./install --check
./install --apply
  1. Check Git, Zsh, GNU Stow 2.4.0 or newer, and development-only verification tools. Older Stow releases cannot safely translate the dot-codex, dot-agents, and dot-zprezto directories.
  2. Print the CachyOS package command for missing dependencies without running sudo.
  3. Initialize and verify recursive submodules.
  4. Create real ~/.codex and ~/.agents/skills target containers before invoking Stow.
  5. Use Stow’s simulation mode to report all conflicts before any backup or target mutation.
  6. Create a timestamped backup with metadata-preserving copies and a manifest that records every original path, file type, mode, symlink destination, and backup path.
  7. Move only the manifested conflicts aside, Stow the selected packages, and verify every installed link inside a transactional shell trap.
  8. If Stow or verification fails, automatically remove links created by that run and restore every manifested original before returning an error.
  9. Provide an explicit restore command that reads the manifest and refuses to overwrite newer unmanifested state.
  10. Print the optional chsh command rather than changing the login shell automatically.
×

Never use stow --adopt in bootstrap

--adopt modifies repository contents. Migration should use explicit, timestamped backups so a conflict cannot silently overwrite the intended source of truth.

07 · Verification gates

Test the home directory without risking the home directory.

Local tests and CI should install into a temporary home, exercise the same commands twice, and fail on secrets, invalid skills, shell errors, or broken dependency pins.

  • Stow simulation and installation into a temporary $HOME.
  • A second installation produces no changes or errors.
  • Unstowing removes managed links without touching unrelated files.
  • zsh -n succeeds for all managed Zsh files.
  • A minimal interactive Zsh startup exits successfully without stderr.
  • Every recorded Prezto submodule is initialized at its pinned revision.
  • CI runs GNU Stow 2.4.0 or newer and exercises --dotfiles translation for directory names.
  • Each skill has one SKILL.md with name and description.
  • Skill references, scripts, assets, and required license files exist.
  • No managed symlink is broken.
  • ShellCheck validates bootstrap scripts.
  • A secret scanner examines tracked content and commit diffs.
08 · Delivery sequence

Four reviewable commits.

Implementation follows the repository rule that complex work is planned first and that each completed plan step is committed separately.

COMMIT 01

Scaffold and safety harness

Add the repository structure, Stow configuration, conservative installer, temporary-home harness, and baseline documentation.

COMMIT 02

Prezto and Zsh

Pin the personal fork, migrate runcom links and Powerlevel10k configuration, reconcile ForgeCode’s path addition, and verify shell startup.

COMMIT 03

Codex and personal skills

Create bundles and hash-verified working-tree archives, import personal skills, deploy global guidance, restore third-party attribution, and enforce the runtime exclusion boundary.

COMMIT 04

CI, recovery, and handoff

Add automated validation, document install/update/uninstall workflows, bundle the parent ~/.codex repository, and remove obsolete Git metadata after verification.

◎

Review gate before every commit

After each implementation phase, spawn a new review agent. Fix every high- and medium-severity finding, repeat review until neither severity remains, report all low-severity findings before continuing, rerun the phase’s verification, and only then create its commit.

Definition of done

The repository can configure a clean temporary home twice without error; a fresh CachyOS machine can follow the documented install path; Prezto and its modules are pinned; Codex loads the intended global instructions and skills; no generated state or credential is tracked; and the former setup remains recoverable from timestamped backups, Git bundles, metadata-preserving working-tree archives, and verified SHA-256 manifests.
